## 资源仓库发布和读取

启动器按固定提交的 `manifests/index.json` 和交付单验证 `manifests/releases/` 内的规范安装目标，不解析厂商字段。维护工具读取同一提交的 `manifests/publisher.json`：`channels[渠道].formal.qualities[画质]` 引用厂商完整目标，`patches[包名][源版本]` 引用 `upstream/<md5>.json`，可用预下载单列在 `predownload`。 [通用安装协议](../game-resource-packs.md#通用安装清单) · [维护索引](../../Game/Wuthering%20Waves/manifests/publisher.json)

鸣潮适配器遍历 TOML 中的渠道和官方登记的画质。每个渠道只读取一次顶层索引，完整清单和补丁原件按摘要去重；任何渠道失败都不会交付新的鸣潮清单。以下命令从资源仓库根目录生成一份独立快照，其中 `--output` 是尚未存在的目录。[快照生成](../../Github/wuthering_waves/publish.py) · [对象校验](../../Github/wuthering_waves/storage.py)

```sh
python3 -B -m Github snapshot --game wuthering-waves --output /tmp/wuwa-new-snapshot
diff -qr 'Game/Wuthering Waves/manifests' /tmp/wuwa-new-snapshot
```

资源仓库的 Actions 统一同步所有登记的游戏。发布策略见[仓库说明](../../README.md#游戏清单更新)。

## 2. 生成目标 JSON 和本机待下载任务

### 本目录脚本的实际输出

| 输出字段 | 值从哪里来 |
| --- | --- |
| `game`、`channel`、`quality`、`source` | 游戏名来自 TOML，渠道与画质来自参数或默认值，`source` 记录成功读取的渠道索引 URL |
| `version`、`packs[].version` | 顶层取 `resourcePacks.common.version`，每个分包保留自己的 `version`。脚本在合并前核对各分包与公共包的版本一致 |
| `packs[].index_url`、`packs[].index_md5` | 分包清单的实际请求地址和发布索引给出的 `indexFileMd5`。脚本对解开 gzip 后的原始 JSON 字节验 MD5，再解析 |
| `files[]` | 每项有 `pack`、`path`、`url`、`size` 和 `md5`。官方条目带有非空 `chunkInfos` 时，脚本检查分块连续、从 0 开始并覆盖整个文件，输出 `chunks`，两端偏移都计入块内 |
| `file_count`、`total_size` | 各分包先将文件字节数合计与 `unCompressSize` 核对。合并时以忽略大小写的路径为键，大小与 MD5 均相同的重复文件只计一次，冲突会报错 |

生成器的字段和校验分别见 `read_document`、`chunks_for`、`read_pack`、`merge_files`、`manifest`。脚本的 `published_cdns` 还要求节点的 `P > 0`，按权重降序尝试镜像，并对各镜像返回的分包清单使用同一发布摘要。输出文件在同目录临时文件写完后替换。CLI 默认选国服官服和 HD。[manifests.py][manifests] · [sources.toml][game-config]

在资源仓库根目录运行以下命令，可查看 B 服 HD 目标清单的摘要。`jq` 只用于查看结果；要保存完整 JSON，可传 `-o 文件名`。

```sh
python3 -B -m Github wuthering-waves fetch --channel bilibili --quality HD |
  jq '{channel, version, quality, file_count, total_size, packs: [.packs[] | {name, version, file_count}]}'
```

## 3. 换服时哪些文件可以复用

`ww checkout` 把用户所选的渠道作为目标。管理器从游戏目录的 `launcherDownloadConfig.json` 读取 `appId`，映射为当前服。没有可识别的登记时，`_detect_current_server` 回退到管理器的 `server_type`。这个 CLI 入口用目标服构造管理器，所以此时返回的是命令参数，磁盘上的实际渠道仍待确认。[cli.py · checkout][cli_checkout] · [core.py · _detect_current_server][detect] · [渠道映射][appid]

**官服与 B 服快速切换。** 参考项目先分别取源服和目标服的基础文件表。对 3.8 结构，这里读取的是 `common.indexFile`。快速切换在这两份表之间按原始 `dest` 和 MD5 比较，范围限于基础清单。`same` 表示两份远端记录相同，此分支直接跳过这些路径。[core.py · _fetch_server_context][server_context] · [_normalize_channel_index][normalize] · [_compute_diff_sets][diff]

| 比对结果 | 参考项目的动作 |
| --- | --- |
| 两服同路径、同 MD5 | 复用共享文件 |
| 同路径、不同 MD5，或只有目标服需要 | 有源文件且尚无源服备份时先备份。目标服缓存的 MD5 匹配就恢复，否则从目标服 CDN 下载并回填缓存 |
| 只有源服需要 | 目标差异文件处理成功后，将源服独有文件备份到该服缓存，并从活动游戏目录移出 |

差异缓存按渠道保存于游戏目录的 `wwm_server_diff_cache`。缓存已有的主、次版本与目标不同且双方均可解析时，参考项目先检查待下载空间，再重置差异缓存。涉及国际服的跨服切换，或指定 `--force-sync` 时，走目标服的强制 MD5 同步，匹配文件仍可复用。[config.py · DIFF_CACHE_SERVERS][cachecfg] · [切换分支][checkout] · [缓存处理顺序][cache_flow] · [备份和隔离][isolate] · [目标文件下载][cache_download] · [缓存命中与空间不足测试][t_cache]

**同版本也有实际差异。** 按 `3.8.0` 官方 `common` 原件，以官服为源、B 服为目标计算，799 个路径同 MD5、21 个同路径不同 MD5、71 个仅 B 服有、0 个仅官服有。例如 `Client/Binaries/Win64/ThirdParty/KrPcSdk_Mainland/KRSDKExternal.exe` 在两服都是 200,904 字节，官服 MD5 为 `7de0d631e18a6f449835daa3413e9250`，B 服为 `47042d8c3121d46ceb645d3923c88f84`。这 21 + 71 项是缓存检查前的候选数，用户实际需要下载多少还取决于目标服缓存。[官服 common 原件][cn-common] · [B 服 common 原件][b-common] · [比对算法][diff]

## 4. 游戏版本更新和预下载

参考项目的游戏更新入口是 `ww predownload`，`ww predownload --apply` 应用已经取得的更新。`ww incremental` 是兼容别名。另一个命令 `ww update` 更新的是 `ww-manager` 工具自身。[cli.py · predownload 和 incremental][cli_patch] · [cli.py · update][cli_self]

### 选哪个版本、哪个包的补丁

1. **先确定本地状态。** `wwm_resource_state.json` 记录 `active_tier`、各包版本和 `incomplete`。`common` 的记录还带 `common_server`。兼容旧安装时，公共包和当前为 HD 的旧安装可以从 `launcherDownloadConfig.json` 取版本，其他画质的回退路径会核对 `bundles` 登记和 `launcherDownloadConfig/<pack>.json` 标记。[core.py · resource_pack_version][state] · [_record_resource_pack][record]
2. **选择发布目标。** 对 `common` 和当前画质分别读取正式版。两者本地版本均已等于正式版时，才考虑正式索引中的 `predownload`。预下载段须含受支持的分包结构。已完成的同版本包可跳过，标为未完成的同版本包会触发修复提示。[resource_updates.py · _create_plan][plan] · [分包匹配条件][match] · [正式版与预下载优先级测试][t_pre]
3. **按源版本精确匹配。** `resourcePacks[包].version` 是目标版本，`patchConfig[].version` 是该补丁接受的**已安装源版本**。匹配成功后读取这条补丁自己的 `indexFile`。缺少对应分包补丁会中止计划，调用方可显式选择全量修复。这里不会猜最近版本，也不会自动改装 HD。[incremental.py · _find_matching_patch][patch_pick] · [缺少补丁的测试][t_patch_missing]
4. **B 服单独核对公共包。** 对 `common` 的完整文件和差分输出，参考项目要求路径、大小和 MD5 与 B 服目标清单相符，并检查删除项。正式更新缺少目标清单时会报错。预下载阶段目标清单尚未开放时可暂缓 `common`，之后再补。[resource_updates.py · B 服目标清单选择][bili] · [目标文件对照][bili_check] · [B 服预下载测试][t_bili]

### 把补丁索引翻译成下载任务

| 补丁字段 | 含义及如何使用 |
| --- | --- |
| `resource[]` | 带路径、大小、MD5 的传输记录，可包含完整文件和差分文件。完整文件优先采用条目的 `fromFolder`，缺省时采用全量资源目录。差分包优先采用匹配补丁的 `baseUrl` |
| `groupInfos[].dest` | 指向一个差分传输文件。分包更新器要求它在 `resource[]` 中有对应记录，用传输文件自身的大小和 MD5 校验 |
| `groupInfos[].srcFiles`、`dstFiles` | 分别描述应用补丁所需的旧文件和要生成的新文件。一个差分组可以有多个输入或输出，计算差分包的下载量时使用传输记录的大小 |
| `deleteFiles[]` | 应用阶段处理的旧路径。分包校验拒绝同一补丁同时写入和删除同一路径 |

源代码分别给出了索引校验、差分 URL、完整文件 URL 和本地待传输任务。完整文件可从游戏目录或暂存目录命中，差分文件可从补丁缓存命中。[resource_updates.py · validate_index][patch_schema] · [incremental.py · 差分地址][diff_url] · [完整文件地址][full_url] · [pending_download_tasks][transfers]

**实际补丁样例。** 国服官服 `common` 的 `3.7.1 → 3.8.0` 索引有 43 条 `resource` 记录，其中 39 条对应差分组、4 条是完整文件，另有 28 条 `deleteFiles`。同一个差分包在 `resource` 和 `groupInfos` 中各出现一次，统计传输文件时只计一次。其发布索引给出的 `indexFileMd5` 为 `68ee881a3d9e9b2f2aaa7dfc18ab4e77`。[该版本的官方补丁索引][cn-patch] · [传输记录与差分组的关联][patch_schema]

## 5. SSMT4-Linux 的资源包风控规则

**风控由每个游戏的资源包配置定义。** 配置指定要处理的文件、动作、字段和新旧值。资源包脚本负责确定下载清单，核心负责执行适用的文件操作并记录结果。上一节的 `deleteFiles[]` 来自库洛补丁索引。本节记录 SSMT4-Linux 的需求，其中风控“删除”的含义固定为**给完整文件名追加 `.disable`**。

规则放在游戏已有的 `sources.toml`。下面的 TOML 展示脚本能读取的字段，三个 `example/` 路径均为示例。生产规则目前为空。有真实规则时，脚本按目标条件输出动作交给核心。[游戏配置][game-config] · [风控计划实现](../../Github/wuthering_waves/rules.py)

```toml
[[risk_control.rules]]
action = "disable"
path = "example/legacy.txt"

[[risk_control.rules]]
action = "set_field"
path = "example/settings.json"
format = "json"
key_path = ["ABC"]
from = "102"
to = "205"

[[risk_control.rules]]
action = "replace_text"
path = "example/settings.txt"
match = "whole_line"
from = "ABC=102"
to = "ABC=205"
expected_matches = 1
```

| 动作 | 示例的预期结果 | 重复执行或遇到冲突时的建议 |
| --- | --- | --- |
| 禁用文件 | `example/legacy.txt` 改名为 `example/legacy.txt.disable`，保留文件内容和原扩展名。改名可用于文本和二进制文件 | 只有禁用名存在时视为已禁用。两个名字都存在时保留两份并报告冲突。恢复时只撤销执行记录中由本规则完成的改名 |
| 修改结构化字段 | 按键路径定位 JSON 顶层的 `ABC`，把字符串 `"102"` 改为字符串 `"205"`。同名嵌套字段和其他字段保留原值 | 已为目标值时跳过。键缺失、类型不符或原值不同，都报告具体文件与键路径 |
| 修改文本 | 仅将完整的一行 `ABC=102` 改为 `ABC=205`，`ABC=1020` 保持原样。保留原编码和换行 | 先核对匹配次数。旧行消失且已满足目标状态时跳过。出现多个候选或内容已被其他程序改写时，保留原文件并报告 |

内容修改建议覆盖大多数文本配置。TXT、CFG、CONF 等可解码文本可共用精确匹配，结构化文件则按配置声明的格式解析。后续为 TOML、INI、YAML 等格式增加字段定位时，可以沿用“路径、预期旧值、目标值”的规则。

**与更新和转服的衔接。** 建议先按目标渠道的官方清单校验安装文件，再应用该资源包为目标状态声明的风控规则。核心分别记录官方文件摘要和规则执行后的路径、摘要。下次检查时，已禁用的文件或已改为 `"205"` 的配置就能被识别为预期状态。若增量补丁需要原文件，先取回并验证官方原件，完成更新后再应用目标版本的规则。
